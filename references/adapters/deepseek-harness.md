# DeepSeek Harness 适配（adapters/deepseek-harness.md）

DSH 与 WorkBuddy 系的差异集中在三处：**没有会话 id 变量、记录是压缩件、token 读数不稳**。这三处都影响能力上限，但不影响核心流程——本文件的核心任务是说清「哪些能自动做、哪些只能报缺口」。

## 1. 五个接口

### 1.1 `agent_name`

`"DeepSeek Harness"`（官方名，空格保留在条目与标题里，文件名里换下划线 → `DeepSeek_Harness`）。

DSH 没有 WorkBuddy 那种双客户端同核的情形，判定简单：宿主产品标识能取到就直接用。取不到时退到记录路径所在的配置根（如 `~/.dsh/` → `DeepSeek Harness`）。**不做进程扫描、不反推已有文件名**——理由同 workbuddy.md §5，与产品无关。

三者都取不到 → `未知 agent` + 缺口段。环境里若出现从 WorkBuddy 继承来的 `WORKBUDDY_*` / `CODEBUDDY_*`，**不可据以判定**——只看 DSH 自己的数据根。

### 1.2 `session_id`

**没有 `CODEBUDDY_SESSION_ID` 这类变量**（也没有 `WORKBUDDY_*` 系列）。可用来源按可靠性排序：

1. **记录目录名**：DSH 的会话按目录组织，目录名即天然标识；
2. **记录内的会话元数据**（若明文可读——压缩件不行，见 1.4）；
3. **文件 mtime + 启动时间**组合派生：`unknown-YYYYMMDD-HHMM`。

派生结果必须满足 schema.md §1.3 的约束：**不含空格、不含下划线**。目录名若含下划线，先把下划线改成 `-` 再用——**这一步不能省**，否则文件名解析（schema.md §1.2 从右往左取最后一个下划线）会把 agent 名切错。

DSH 标识形态与 UUID 完全不同，schema.md §1.2 的解析刻意不依赖 UUID 正则正为此。若哪天要改解析算法才能支持 DSH，说明接口设计有问题，应改接口而非打补丁。

### 1.3 `session_record_path`

形如 `<DSH 数据根>/<会话目录>/session.v4.jsonl.zstd`。

- **运行时探测**，先确认目录存在再拼路径；
- 同一会话可能有多个版本文件（`session.jsonl`、`session.v4.jsonl.zstd` 并存）→ 文件源段**允许多行**（schema.md §2.2 已允许），每行各带独立状态与核对至；
- 探测不到 → 返回空，该文件不可溯源（不冻结、不判缺口）。

### 1.4 `record_format`

**`jsonl.zstd`（压缩件）**——与 WorkBuddy 最关键的差别：

> **明文 grep 不可用。** 压缩字节里没有可检索的时间戳或关键词，`grep` 只会零命中，且**失败是静默的**（看起来像「这段没有内容」）。

| 能力 | 明文 jsonl | 压缩件（DSH） |
|---|---|---|
| 查缺口（S5） | ✅ 读末行 | ⚠️ 不做 → 报「来源为压缩格式，无法自动核对」 |
| 自动补写 | ✅ grep 定点 | ❌ **禁止** |
| 缺档扫描（S6） | ✅ 列目录 | ✅ 只看 mtime，不读内容 |

**为什么禁止自动补写**：补写要求「定点捞命中行、只读命中部分」，压缩件只能整份解压，正撞硬规则 7（禁止整读会话记录）。**宁可报缺口让人手工补，也不整读。** 若宿主提供能流式输出给 grep 的官方解压工具，可在 adapter 层实现后解除——那是新增能力，不是默认。

### 1.5 `token_output`

**可用但不可靠**。实测同一会话的 `projcache` 读数出现三个不同值（3300 / 1958 / 143），无稳定口径。

处理方式：

- **返回空**，落款省略括号。这是正确行为：读数不可靠时写上去就是假信息；
- 用户当轮明确要求看到数字 → 写读数并**在括号内标明来源不稳**，如 `（Token消耗：输出 3300，读数不稳）`；
- **绝不**取最大值、取平均值或跨轮插值来「估算」——那比不写更糟。

## 2. 可选接口

### 2.1 `record_dir`

DSH 的数据根，只扫这一个根。**不许回退去扫 `~/.workbuddy/` 或 `~/.workbuddy-ai/`**——那是别的 agent 的会话。

### 2.2 `user_turn_extract`

压缩件形态**无法在不解压的情况下提取**，因此：

- 若记录已被外部工具解压为明文 → 按 workbuddy.md §2 的同构规则提取（DSH 的行结构同样是 `{type, role, content[], payload}`）；
- 若仍是压缩件 → 返回空，补写整体跳过（见 1.4）。

## 3. 降级矩阵

| 能力 | 状态 | 说明 |
|---|---|---|
| 写本会话 `mem_` / 结尾信号 / 渲染报告 | ✅ 全功能 | 与记录格式无关 |
| 自检 S1–S4、S6 | ✅ 可用 | S3 越界检查需 `T_start`/`T_end`，取不到则跳过 3.2 并回报；S6 只看目录与 mtime |
| 自检 S5 覆盖 | ⚠️ 降级 | 报「无法自动核对」，不判有无缺口 |
| 交接「缺口补写」 | ❌ 不可用 | 禁止整读 → 只报缺口，等人工补 |

**降级原则的落地检验**：上表里所有 ❌ 与 ⚠️ 都只影响「自动补全」这一类便利，**没有一条影响「记忆写不写得进去、报告能不能出」**。这符合 adapters/index.md §2 第 5 条。
